# 持续陪伴型 Personal Agent：评审与技术方案

日期：2026-10-30

状态：建议方案，供评审；未实施

输入：[产品 PRD](./prd-personal-agent-continuity.md)

## 1. 评审结论

三类预期在产品层面均已覆盖，可以进入技术设计，不需要推倒重写。不能把“PRD 覆盖”视为“现有功能已经支持”，也不能只交付 P1 后就宣称全部满足。

| 预期 | PRD 覆盖 | 交付判断 |
|---|---|---|
| 学习、锻炼进展与停滞纠偏 | §3.3、§4.1–4.3、FR-01/02/06、US-01–06 | 有真实证据、停滞判定、调整实验与效果回顾，闭环完整；P1 验收 |
| 工作依赖、提前风险和重规划 | §4.4、FR-10、US-07/08 | 支持 Vital 内部事实；外部回复需用户更新，不能承诺自动跟进邮件/GitHub；P2 验收 |
| 假期兴趣与现实条件、采纳和核实 | §4.5、FR-07/08、US-09/10 | 流程完整；具体活动发布依赖外部事实能力，只有通用方向不算完整实现现实可行性；P3 验收 |

下面是建议补充的验收口径，不是已经由用户确认的新需求。原 PRD 保持不变。

### 1.1 实现前必须补严的边界

1. **进展不能只按线程关联计数。** §3.3、US-02 未定义一条证据如何抵扣机会。一次完成可能同时来自任务与习惯，也可能只是 agent 准备材料。需要显式成果标准、证据来源、执行主体及机会归属；否则学习进展会虚增。自报与系统记录疑似重复但无法确定时让用户合并，不凭相似文本自动删除。
2. **实验评价不能随新约定漂移。** FR-02、US-05 没有定义实验中途暂停、改节奏、补记和撤销如何影响回顾。冻结原始基线、目标和窗口；中途修改则标为中断/替代，不能继续套新分母判断旧实验有效。
3. **关联变更不能任意部分成功。** US-08 允许冲突项跳过。但“先腾出 A 时段，再将 B 移进去”若只成功后半步，会制造冲突。保留独立项跳过语义，新增依赖组：组内全成或全跳过，组间可部分应用，并对最终排程重验。
4. **假期临近核实需提前于不可逆节点。** FR-08 只规定出发前 24 小时，可能晚于预约、免费取消或交通决策时间。建议已知时在最早决策截止前增加检查；未知时明确标注。选中仅表示进入草案，核实失败不得显示“已确认可行”；用户仍可明确接受待核实状态。
5. **通知去重需要统一的曝光账本。** FR-03 同时涉及晨晚报、周报、推送和前台查看；仅按 outbox 去重不足。必须按候选身份协调各出口，不能将“报告生成了”当作“用户已经收到”。

### 1.2 范围建议

保留 P1 → P2 → P3 顺序。P1 的数据、调度与通知是后二期共用基础。PRD 虽以工作为首要关切，但先打通长期投入是工程交付顺序，不改变工作风险在页面上的优先级。三期分别验收，完整目标在 P3 完成。

本次只做静态代码审查，没有运行服务或证明线上行为。

## 3. 职责与数据流

```text
任务/习惯/用户补记/约定与依赖变化
  → 同事务记录领域事件、递增事实版本
  → worker 按事件或 nextCheckAt 加载当前事实
  → 确定性规则计算机会、进展、风险与候选
  → 按需调用模型准备材料/解释/方案
  → 校验租约、授权和事实版本后保存草案
  → 今天页/报告/通知统一挑选候选
  → 投递前重新校验并预留预算
  → 用户补记/采纳/暂停/应用方案
  → 审计与事件 → 下一次观察/实验回顾
```

规则负责日历、资格、权限、版本、预算、事实计数和状态迁移。模型负责有依据的建议、材料整理与文案，不能直接宣告完成或更改正式安排。模型失败不阻塞事实卡片。

建议新增 `apps/server/src/continuity/`，划分 contracts、evidence、opportunities、evaluate、interventions、experiments、delivery-policy、events；P2 加 work-risk、planning；P3 加 exploration、verification。后台模型 handler 留在现有 agent 执行体系中，调用领域服务提交结果。所有名称均为拟新增，不代表文件已经存在。

## 4. 数据设计

以下是逻辑表拆分建议；迁移编号按实施时仓库最新状态分配。不建外键。用户数据均带 `id/user_id/created_at/updated_at`，所有引用由 service 校验同用户归属。外部 I/O 不放在数据库事务内。

| 阶段 | 建议表 | 关键内容与约束 |
|---|---|---|
| P1 | `continuity_contracts` | outcomeId、生命周期、judgement、currentRevision、authorizationVersion、factsVersion、nextCheckAt、pausedUntil；每用户每线程唯一容器 |
| P1 | `continuity_contract_revisions` | 不可变的意义、阶段成果/完成标准、节奏、时区、最小行动、证据来源绑定、可行动时间、授权范围、生效时间；唯一(contractId, revision) |
| P1 | `continuity_opportunities` | 定时机会或周次数周期；version、windowKey、start/end/checkAt、目标次数、状态、豁免理由；唯一(contractId, revision, windowKey) |
| P1 | `continuity_evidence` | sourceType/sourceId/sourceRevision、actor、occurredAt/recordedAt、事实内容、supersedesId/retractedAt；来源幂等，用户补记带请求键 |
| P1 | `continuity_evidence_links` | evidenceId、contractId、opportunityId、是否满足标准、判断依据；同证据对同约定只计一次，同机会可有多次真实行动 |
| P1 | `continuity_interventions` | kind、事实引用、事实指纹、约定版本、状态、有效期、可行动截止、snoozedUntil、内容与草案引用；唯一候选逻辑键 |
| P1 | `continuity_experiments` | before/after 约定快照、假设、基线、目标、窗口、planId、status、reviewVersion；每约定最多一个 active 实验（部分唯一索引） |
| P1 | `continuity_events` | aggregateId、sequence、type、payload、processedAt、重试；业务写入同事务落事件，消费幂等 |
| P1 | `continuity_exposures` | candidateId、surface、reserved/sent/seen/handled/failed、budgetClass、periodKey、outboxId、时间；候选处理与预算账本 |
| P1 | `continuity_memory_suppressions` | 用户删除的推断主题与来源证据指纹；仅阻止相同旧证据再生 |
| P2 | `continuity_dependencies` | blockedEntity、prerequisiteEntity 或人工外部条件、status、resolvedAt、revision；内部依赖拒绝自环及环路 |
| P2 | `continuity_protected_blocks` | 用户明确保护的时间区间/重复规则、时区、版本；不以文本记忆代替排程硬约束 |
| P3 | `exploration_windows` | 日期、时区、region、calendarVersion、用户空闲确认、closedReason；同一逻辑窗口唯一，日历更新不重新轰炸 |
| P3 | `exploration_proposals` | windowId、activityKey、兴趣原因、约束、状态、planId、decisionDeadline、departureAt、nextVerifyAt；窗口最多三项由事务锁保证 |
| P3 | `exploration_verifications` | proposalId、阶段、字段事实、URL、fetchedAt、有效期、verified/unknown/changed、前后差异；保留失败记录 |

补充：用户级 continuity 设置保存探索独立开关、外部检索授权、预算参数、默认节奏。长期关切首期复用可编辑手动记忆；约定保存 concern 引用及意义快照，不强制目标树。结构化排程约束仍写保护时间表。

主要索引：`(user_id, lifecycle, next_check_at)`、未消费事件、候选 `(user_id,status,expires_at)`、证据 `(user_id,occurred_at)`、依赖反向查找、核实 `next_verify_at`。事件/机会/候选的状态与版本字段设 CHECK；历史归档保留审计但不参与活跃扫描。

## 5. P1：长期投入闭环

### 5.1 激活、机会和进展

- 生成草案不创建正式任务。激活事务锁定约定容器，保存不可变版本与授权、首批机会、事件和已明确确认的动作；相同请求键返回原结果。
- 周期以约定时区计算，UTC 存储边界，保存本地日期与时区快照。周定义建议周一至周日；首期激活的残缺周只观察，不触发周未达约，随后首个完整周开始判定。
- 定时机会结束后 12 小时检查；连续两个有效机会无证据触发。周次数按完整周期结束后 12 小时检查，不生成虚构时段。
- 定时机会优先使用明确绑定/用户指定的记录；仅凭时间无法确定归属则不自动抵扣。周次数按 occurredAt 归属并去重；同一行动不能抵扣多个定时机会。允许晚录入和明确补记。
- 只认约定接受的证据和真实用户行动。agent 生成材料、收藏增加、改标题不计进展。用户声明“已做过”可直接作为自报证据，不要求证明。
- 撤销完成、修正补记与证据合并重新计算受影响机会、候选和实验回顾；已发通知无法收回，详情显示已解决，不再重发同风险。
- 暂停/休假/取消机会记录豁免。恢复只生成未来机会；变更时区不改历史归属。改节奏关闭旧版未来机会，避免新旧版重复计数。

### 5.2 纠偏实验

候选建议 → 用户确认方案 → 正式写入成功 → 实验 active → 窗口结束 review_ready → 回顾 → completed/中断。

实验只在必要的方案依赖组全部成功后开始。基线取调整前完整可观察周期，保存有效机会数、真实进展和用户自报；无基线时明确无前后比较。回顾分别展示“实际做了什么”“达约情况”“用户是否觉得更易开始”，不把一次行动归因为实验成功。

中途改约定：结束为 superseded，并提供启动新实验的草案；暂停：结束为 interrupted，恢复后不偷改旧窗口。补记可提升 reviewVersion，保留原回顾和修订原因。无响应不自动升级实验或生成更多学习任务。

## 6. 持久执行、通知与记忆

### 6.1 调度与并发

- 业务事务中写事件并递增 factsVersion；禁止 commit 后仅 fire-and-forget 触发，否则崩溃会丢掉重算。
- worker 消费事件进行规则重算；按 nextCheckAt 扫描到期机会、实验和恢复日期，建议分钟级；每日补扫修复漏调度。不能把“每日补扫”当作风险或核实的唯一时钟。
- 继续使用 agent_jobs 的租约和恢复机制。模型调用前记录约定/权限/事实版本；提交效果时同事务检查当前版本和租约。旧结果丢弃并标记待重算。
- 普通事项每日最多一次自动模型评估，以本地日和 contractId 原子抢占；事实变了可以立即重新跑规则。相同输入指纹复用输出；用户请求仍计总成本预算。
- 普通材料准备的产物写草案或明确标记 agent actor，不能走自动完成用户学习任务的路径。

### 6.2 候选生命周期与预算

候选为 open → snoozed / accepted / dismissed / resolved / expired / withdrawn；seen 是独立曝光事件。普通候选七天过期；连续两次真正未响应后记录仅站内截止日期 14 天，期间不排推送，结束后需要新机会产生的新候选。

同事项普通纠偏另有七天推送冷却，以曝光账本的最近实际发送时间为准；重建候选、修改文案或约定版本不能绕过。候选过期与推送冷却分别计算。“晚点再说”默认 snoozedUntil 为三天后，用户可指定日期；唤醒仍检查七天冷却和当前事实。回放必须覆盖新候选出现但仍在冷却内的情况。

统一策略服务供今天页、晨晚报、周报、直接通知调用。预算定义为新能力的主动推送每日 1 次/每周 3 次，不额外吞掉用户手动设置的普通任务提醒；报告夹带同候选视为候选曝光。报告生成时可短期预留出口，发送失败/内容变更释放预留；实际投递成功才记覆盖，模型生成报告不算投递。

预留预算时锁定用户预算范围，计入当期 sent + reserved，防止多个 worker 并发超额。重试复用预留；跨本地日/周重验预算。发送前再次加载当前约定、事实版本、候选有效期、用户设置、处理状态与安静时段。前台看到候选后标记仅站内；已处理直接关闭。

工作风险例外：已接受承诺、有可信最晚启动时间且不足 24 小时，同风险版本一次、额外每日一次；仍遵守安静时段。风险指纹来自依赖/截止/估时/占用等事实变化，不因改写文案获得新配额。延迟后已越过行动截止则撤回，必要时建立新的“已逾窗口”站内事实，不继续发送过时建议。

新 outbox 事件建议 `agent.continuity`，payload 主要保存 candidateId 与版本，不信任排队时的旧文案。共享 candidateId 使报告与推送互斥选取。外部渠道发送不能与数据库提交原子化：采用稳定投递键和渠道幂等（若支持），超时未知状态留痕并对账，不能承诺物理网络投递绝对 exactly-once。暂停可阻止发送前尚未发出的请求，不能撤回渠道已接收的消息。

### 6.3 记忆修正

沿用 agent_memory/history，补充来源证据指纹与适用事项。manual 修正优先；删除推断同事务写 suppression，所有新蒸馏写入路径都检查 suppression，检索删除失败可重试且读取时过滤已删除 ID。新证据可提出待确认新判断；一次拒绝活动不产生永久主题禁令。

## 7. P2：工作依赖与重规划

依赖保存内部 task/outcome 或外部人工条件。内部完成事件沿反向依赖索引唤醒；撤销完成重新阻塞。外部条件只由用户更新，显示最后更新时间与“等待你更新”。

最晚启动计算使用显式剩余估时、截止、可工作窗口、已有占用和保护安排，从截止向前装箱。首期采用用户显式顺序/依赖 DAG 与单人资源约束的保守排程，不宣称通用最优解。任务是否允许拆分需显式字段；不可拆分任务需要连续空档。共享空档不能被多个承诺重复使用。

缺失估时、未知依赖解除时间、日历覆盖不足分别输出“风险待确认”和缺失项；不得采用排程器的 30 分钟兜底推断确定延期。已知依赖未完成时可计算“最晚需要解除时间”，不能假定届时一定解除。全天保护安排明确占满相应可行动时间；普通全天截止任务不等同全天占用。

preview 保存全部受影响实体版本、前后差异、保护安排版本与依赖组。应用事务锁定相关实体、验证最终时间可行性，独立项允许跳过，依赖组整体跳过；返回 applied/skipped/需要重算。正式任务变化、实验激活、约定变更、审计、事件必须同事务完成。需要从现有 plan handler 抽取可接受 tx 的领域执行器，不能串联多个各自提交的 apply 调用。

undo 复用审计语义，同时撤回对应约定/实验效果并触发重算；只逆转仍与应用后版本一致的项，后续用户修改不可覆盖。跨事项冲突的预览必须展示家庭/休息等保护块的影响，模型不能自行取消保护。

## 8. P3：探索、采纳与现实核实

### 8.1 窗口与推荐

以公共日历 + 明确工作安排 + 用户空闲窗口组合判断；region 需显式设置，不能把表默认 CN 当作用户地区。给 holiday 数据增加导入元数据（来源 URL、抓取时间、有效覆盖范围/年份及版本）；覆盖未知或过期时只用用户确认窗口。

至少连续两个非工作日的候选窗口提前十天检查；开启较晚可补生成一次。普通周末开关默认关闭，每月最多一次。窗口身份稳定，sourceVersion 更新触发重算但不绕过去重。用户选择休息关闭窗口。

兴趣从明确记忆和近期反馈读取；事实条件包含城市、时间、同行、出行方式、预算、精力。缺少决定性的条件只追问一项，或给无位置依赖方向，不默认家庭结构或有车。生成最多三个有差异方向，并为自由时间留块。

### 8.2 外部事实适配器

新增统一接口 `search / verifyActivity / weather`，实现供应商在 P3 开工时另行选型和验证，不把内部 search.all 当实现。每次返回字段级 URL、查询时间、有效范围和 verified/unknown；价格、开放、预约、交通不能以模型记忆填充。

请求只发送必要地点、日期、活动词，不发送私人背景全文。网页作为不可信资料处理，不能触发权限升级或写操作。抓取若支持任意 URL，限制协议、内网地址、重定向和大小。超时/费用上限/熔断统一纳入 capability 观测。

### 8.3 采纳与核实状态

proposed → selected → verification_pending → draft_ready → confirmed → completed/取消。

选中后重核实并准备草案；正式安排由用户确认，事务保存 proposal→task 映射和幂等键。检索失败显示 unknown，可由用户明确接受待核实安排，不能静默当作核实通过。出发时间/地点改变递增版本并重建核实计划。

检查时机：初次生成、采纳时、已知最早决策截止前、出发前 24 小时内。查询天气需在可用预报范围内；范围外保存待查时间。只在影响成行的实质变化时通知，提供替代或延期草案，不擅自修改安排。实质变化去重按相关事实指纹，不按查询次数。

活动级 activityKey + 地点/主办方用于 90 天拒绝去重，主题只降权。出行后下次前台可轻问一次；无回应保持未知。P3 具体本地活动功能旗标只有在外部事实适配器及发布用例通过后开启。

## 9. API、聊天与 UI

拟新增 `/api/v1` 下的接口，共用领域 service，客户端和聊天不各写一套规则：

| 路径/动作 | 用途 |
|---|---|
| `GET/PUT /outcomes/:id/continuity` | 读取摘要、创建/修改草案，返回版本 |
| `POST /outcomes/:id/continuity/{activate,pause,resume,end}` | 生命周期与授权变更 |
| `POST/PATCH/DELETE /continuity/evidence[/:id]` | 自报、修正、撤回；DELETE 表示业务撤回 |
| `GET /continuity/interventions` | 今天页有效候选，含事实来源与主要操作 |
| `POST /continuity/interventions/:id/{seen,feedback,snooze}` | 曝光与反馈；seen 必须幂等 |
| `GET /continuity/experiments/:id` | 基线、实验状态及版本化回顾 |
| 现有 plan preview/apply/undo 的扩展 | 所有正式任务、节奏及跨事项变更 |
| `GET /exploration/windows/:id`、提案 select/confirm/rest 动作 | 探索详情、采纳与关闭窗口 |

写请求携带 expectedVersion 与请求幂等键，版本冲突返回 409 和当前版本；跨用户引用返回 404。涉及多实体的确认绑定具体 previewId/摘要版本，“按这个改”通过现有会话 gate 解析，不能凭模型自由选择旧方案。

DTO 在 `packages/dto` 定义；摘要加入 OutcomeDetail/TodayDashboard 或独立查询，避免把历史证据和正文塞进列表。今天页最多三条，只默认展开第一条；ThreadWorkspace 加托管摘要、进展补记、实验回顾与依据抽屉；探索详情独立路由。草案和正式日程区分，失败/离线/未知状态独立呈现。所有 mutation 刷新 today、线程、候选及关联任务缓存。

## 11. 清理、上线与运维

- 硬删线程同事务撤销授权、删除/解除约定及子记录、取消 jobs/outbox、清理依赖与预览引用，保留审计只能保留去标识元数据；已经运行的任务必须因父对象不存在而拒绝落地。删除后索引清理走可重试事件。
- 软删除保留证据和历史，暂停所有未来效果；恢复仅重建未来窗口。删除任务/习惯时解除绑定、撤回其有效证据并重算，防止孤立进展。
- 新表加入 `apps/server/__tests__/helpers/db.ts` 的 resetDb 和 eval 按用户清理。数据库迁移后重启 worker；本次只写设计文档，不修改 schema 或重启进程。
- 旧用户保持未托管；分期旗标控制写入口、调度及投递。关闭旗标时停止新效果，但保留只读与用户暂停/清理能力。回滚优先关旗标，不破坏性删历史。
- 观测：到期检查延迟、事件积压、过时结果丢弃数、候选撤回原因、预算抑制、核实未知率、LLM 成本；产品指标沿用 PRD，未响应与失败分开。
- Web/桌面发布前 bump `apps/web/package.json` 后再构建。正式发布需完成该期回放与浏览器验收；静态方案评审不替代运行验证。

## 12. 最终验收场景

1. 学习/锻炼：激活 → 两个机会无记录 → 给出事实与最小行动 → 用户调整 → 实验开始 → 补记真实行动 → 旧提醒撤回 → 周期回顾；同流程验证中途暂停与撤销进展。
2. 工作：依赖未就绪 → 按可信工作量计算最晚解除/启动窗口 → 提前风险 → 用户接受整体方案 → 某项并发改期导致依赖组跳过 → 重算 → 依赖完成撤回旧通知。
3. 假期：识别已确认空闲窗口 → 三个以内差异化方向 → 采纳重核实 → 确认安排 → 决策截止或临近出发核实发现变化 → 提供替代 → 用户决定 → 结束后轻反馈。

三条都跑通，才达到本次提出的完整预期。实际是否更容易开始、工作风险是否有用、探索是否值得，仍需真实使用观察，不由测试通过推断。
