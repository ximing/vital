# PRD：Vital 持续陪伴型 Personal Agent

日期：2026-10-30  
版本：v1.0，产品评审稿  
范围：工作跟进、长期投入与纠偏、节假日探索  
关联：[现有 Personal Agent PRD](../docs/personal-agent-prd.md)

## 1. 产品定义与问题

Vital 是一个持续理解用户所重视的事情、观察变化、帮助推进并适时提出新可能的个人助理。

用户已将个人任务集中到 Vital，但目前仍需要自己想起目标、检查进展、发现停滞、重新制定计划。Agent 已具备部分记忆、后台任务和提案能力，体验仍偏向操作后的整理与反馈。

本轮解决三个具体问题：

1. 工作事项需要持续跟进，在依赖解除、计划变化、承诺即将失守时提醒，并准备下一步。
2. 算法学习、Agent 学习、锻炼等重要但不紧急的事情，经常被短视频等即时活动挤占；连续没有进展时，缺少反馈和有效纠偏。
3. 节假日容易沿用日常惯性，需要更主动、不同于平时的建议，帮助用户理解和探索世界，也为家庭相处创造机会。

健康、家庭和人生价值是长期关切。产品帮助用户把关切落实到选择和行动，不对其人生、关系或自律程度评分。

### 1.1 已确认的用户事实

- 首先关注工作；同时关心健康、家庭和长期价值实现。
- 想系统学习算法和 Agent，但长期未真正推进；锻炼也有类似问题。
- 用户明确提到短视频会占用时间，需要停滞反馈和纠偏。
- 希望节假日有更积极、区别于平时的探索建议。
- 产品交互、审美、介入策略由产品设计负责，不逐项要求用户选择。

### 1.2 产品默认决定

以下为本 PRD 的设计决定，不冒充用户已表达的偏好：采用温和但明确的事实反馈；默认少量主动推送；先在 Vital 内形成闭环；生活选择由用户决定；低风险准备工作可在开启托管时授权自动执行。

## 2. 目标、非目标与方案选择

### 2.1 目标

- 用户交代一次后，事项在多天、多次会话间仍被持续跟进。
- 停滞时给出降低启动成本的具体行动，并检查调整是否奏效。
- 工作变化触发重新判断；提醒发生在仍有行动余地的时候。
- 重要但不紧急的投入能参与跨任务时间分配。
- 假期建议兼顾兴趣、陌生体验、休息和现实约束，能直接转为安排。
- 用户能随时理解、纠正、暂停 agent 的判断与行为。

### 2.2 不做什么

- 首期不做短视频监控、应用封锁、后台屏幕录制或自动读取设备使用记录。
- 不以打卡连续天数、排行榜、羞耻文案驱动使用；不制造补欠任务。
- 不自动推断心理诊断、身体疾病、家庭关系质量；不提供诊疗或运动处方。
- 不要求用户先建立完整人生目标树、填写人格问卷或记录所有生活活动。
- 不自动报名、付款、联系他人、改外部日历；不承诺首期通用浏览器代办。
- 不把所有收藏、愿望自动升级为需要持续督促的目标。

### 2.3 方案取舍

| 方案 | 优点 | 主要不足 | 决定 |
|---|---|---|---|
| 增强提醒与每周报告 | 改动小，复用现有能力 | 缺少跨轮次跟进，容易重复催促 | 作为输出渠道 |
| 以聊天为唯一中心 | 表达自然，容易委派 | 状态和承诺埋在历史中，仍需用户主动打开 | 作为输入与讨论入口 |
| 事项持续托管，聊天与页面共享状态 | 有明确责任、进展、下一步和介入条件 | 需要结构化状态与反馈闭环 | 采用 |

## 3. 核心模型

### 3.1 长期关切、事项与行动

- **长期关切**：身体健康、家庭陪伴、独立创造等，没有强制终点；只保存用户明确表达的意义与希望保护的安排。
- **托管事项**：有持续跟进需要的对象，如系统学习算法、保持锻炼、完成项目发布。界面沿用现有「线程」语义，提供「让 Vital 跟进」，不新增另一套平行项目系统。
- **行动**：可由用户或 agent 完成的具体下一步，复用任务、习惯和代办。
- **探索提案**：围绕假期或可用时间的有限建议；采纳前不生成任务，不计入承诺。

一个事项可关联多个关切，但无需先建关切才能开始。现有线程/目标不自动开启托管。

### 3.2 托管约定

每个事项维护：名称、为什么重要、当前阶段成果、节奏或截止日、最小行动、进展来源、可行动时间、已知阻碍、允许自动准备的范围、下次检查条件、版本。

用户一句话即可生成草案。Agent 只在缺失事实会显著改变内容时追问，例如算法学习的当前基础与用途；其他字段给出可编辑默认值。一次最多追问一个关键问题，不以问卷阻塞首次行动。

默认提议每周两次、每次 20 分钟的学习试行节奏，首个评估窗口为两周；这只是起始草案，开启托管时一并确认。运动强度不套用该学习默认值，采用用户已有活动或先提供低门槛日常活动选项。

### 3.3 状态与证据

托管生命周期：草案 → 跟进中 → 暂停 / 已结束。暂停可带恢复日期；没有恢复日期则等待用户恢复。

跟进中的判断状态：按约推进、待观察、需要调整、等待条件。执行中的准备任务独立记录，不能混同用户进展。

进展证据分三种：

1. 用户自报：一句话记录、补记、确认线下已完成。
2. 系统观察：关联任务完成、习惯记录、用户提交的学习产物。
3. Agent 推测：候选关系或可能的阻碍，不计入已完成进展。

任务改名、重新排期、打开文章、agent 生成学习材料均不自动计为用户学习成果。用户可将阅读本身设为阶段目标；是否达到目标按该约定判断。记录同时保存实际发生时间和录入时间。

## 4. 关键体验

### 4.1 算法学习：从愿望到可恢复的投入

用户说「一直想系统学算法，帮我持续跟进」。Agent 根据基础和用途，生成一个近期阶段与第一步，而非一次铺满数月课程。

默认只展开未来一周的最多三个行动，后续阶段保持概要。每个行动给出主题、预计耗时、完成标准和可直接打开的材料。首次可以是做一道基础题并解释思路，不强制考试。

当两次约定机会都没有进展记录：

> 上周约定的两次学习还没有记录。如果已经学过，可以补一句；如果没开始，我准备了一个 10 分钟入口，我们可以先把节奏调小。

操作为「开始这一步」「调整安排」「已经做过」，次级入口为「暂时不跟进」。不得使用「连续失败」「欠了两次」等描述。

若用户反馈「下班只想刷视频」，记录为用户自述的情境。提出一个试行方案：将一次学习移至午休，提前准备单一练习入口。运行一个约定周期后，再检查是否更容易开始。

### 4.2 Agent 学习：防止收藏替代学习

把一个小型可验证产物作为阶段成果，例如运行一个工具调用示例并解释失败路径。关联收藏作为材料，不因收藏数量增加就宣称进展。

Agent 可自动整理用户已有资料，准备练习和检查要点；不能替用户完成后宣称用户已经掌握。涉及代码、API 等易变化知识的新增外部材料必须检索并注明来源与查询时间。

### 4.3 锻炼：中断后容易回来

按用户选择的活动与节奏跟进。中断后提供缩短、换时段、换活动或休息的选项；不要求补做错过的训练。

用户说明生病、疼痛或需要恢复时，停止强度提升建议，允许暂停。产品只记录自述和安排，不将运动打卡等同于身体健康结论。

### 4.4 工作：在仍能改变结果时提醒

托管事项保存交付日期、关键依赖、剩余工作估时与已知占用。估时足够时，计算最晚启动窗口；缺少估时时说明「风险待确认」，不编造必然延期。

> 周四验收前还需要一次测试，目前接口仍未就绪。按你记录的工作量，明天下午是开始测试的最晚窗口。我已整理影响范围和两个调整方案。

依赖完成后，将事项从等待条件恢复到可推进；原提醒在投递前失效。首期只观察 Vital 内的变化和用户反馈，外部回复未接入时明确显示「等待你更新」。

### 4.5 假期：为探索创造机会

假期前提出最多三个方向：熟悉兴趣的延伸、适度陌生的体验、低精力或与家人共同参与的选择。不是每次必须凑满三项。

每个提案包含推荐原因、体验内容、时间与交通成本、费用范围或待核实状态、同行适配、来源、核实时间、可取消条件以及必要的替代方案。不可只列景点名字。

城市、可用时间或同行信息缺失时，只询问当前推荐必需的一项，或先展示无需位置的探索方向。不得根据语言默认用户所在城市、家庭结构或有车。

用户选中后才生成安排草案；确定后纳入现有日程。活动结束后可在下次打开时轻问「有什么想再体验」，不追问游记，不把未反馈标为失败。

## 5. 主动介入规则

以下为首版可配置默认值，均需通过使用数据验证，不宣称为心理学结论。

### FR-01 触发与判定

- 首次激活约定后才计算履约机会，不追溯历史欠账。
- 定时约定：约定时段结束后 12 小时仍无记录，计为一次「未观察到进展」。暂停、休假豁免及用户取消的机会不计入。
- 周次数约定：以用户本地周为周期，结束后 12 小时检查；不足视为一个未达约周期，不虚构错过的具体时段。
- 两次连续定时机会无记录，或一个完整周次数周期不足，生成一次调整候选；单次错过仅在详情中保留。
- 无节奏、无截止的愿望不判断停滞；开启托管时提议节奏，未接受则仅保留愿望。
- 工作事项由依赖变化、截止变化、时间冲突、最晚启动窗口触发，不套用学习阈值。
- 所有候选都必须包含事实来源、为什么现在需要关注、建议下一步以及可撤销条件。

### FR-02 干预策略

| 已知情况 | 默认策略 | 不允许 |
|---|---|---|
| 没有记录，原因未知 | 允许补记，提供最小行动 | 断言偷懒或沉迷 |
| 用户表示时间不足 | 减量、换时段、指出与其他承诺的冲突 | 自动挤掉家庭或休息 |
| 难度太高 / 不知如何开始 | 降低难度、补一个前置知识、准备材料 | 继续扩展学习清单 |
| 用户表示分心 | 设计一次更容易启动的时间与环境实验 | 没授权就限制设备 |
| 状态差 / 生病 | 降载或暂停 | 将休息标为失败 |
| 目标已不重要 | 修改、归档或暂停 | 说服用户必须坚持 |

单事项同时最多一个有效纠偏实验，记录旧方案、新方案、假设、起止窗口、预期观察与实际结果。实验默认持续一个约定周期；只有一次新记录时描述事实，不推断因果。

### FR-03 提醒预算与静默

- 新能力默认每日最多一次非紧急主动推送、每周最多三次；晨报、晚报和周报中已包含同一候选时，不另发推送。
- 同事项普通纠偏推送冷却七天；「晚点再说」默认暂停该候选三天，可改日期。
- 普通候选七天未响应则关闭，记为未响应而非拒绝；两次连续未响应后，该事项进入 14 天仅站内展示期。之后有新机会未达约才可重新生成，不能重发旧文案。
- 已接受、有明确截止的工作承诺，在已知最晚启动窗口距离当前不足 24 小时时可突破普通预算；同一风险版本最多一次，额外推送每日最多一次，仍遵守安静时段。
- 安静时段延后投递后若已失去行动价值，则撤回通知，在详情留痕。首期不提供强制穿透。
- 用户在前台看到且处理候选后不再推送；仅看到未操作则保留站内，不立即追加推送。
- 假期提案参与同一普通预算，不能另开一条无限制推荐流。

### FR-04 投递前复核

投递前检查事项状态、约定版本、最新进展、候选有效期、是否已处理、静默设置和预算。完成、暂停、改期、删除或相关条件变化后，旧候选撤回或重新计算，不继续按旧计划发送。

### FR-05 准备与执行权限

开启托管时一次性展示并保存范围：默认允许读取该用户已授权的相关 Vital 数据、整理材料、生成练习或计划草稿、按预算执行准备任务。外部检索单列开关。

调整日期、优先级、周期、创建正式任务等通过可预览方案应用；草稿不能占用正式日历。用户一句明确的「按这个改」可作为确认，不重复要求点击。跨事项调整必须显示全部受影响事项。

外部发送、报名、支付和对外承诺首期不执行。取消托管须取消待启动任务；已在运行的任务在产生业务效果前再次校验授权版本。

### FR-06 学习与生活反馈

补记、修正和撤销进展会重算当前判断；用户可在卡片上快速指出「已经做过」「原因不对」「建议不适合」「不再关注」。不要求写解释。

修正当前事实即时生效；泛化成长期偏好时保留证据与不确定性。一次拒绝某活动不代表永久不喜欢该类别。

## 6. 节假日与探索规则

### FR-07 可用窗口

- 复用现有 holiday_calendar 的 region、holiday/workday 与 sourceVersion；节假日不直接等同于用户休假。
- 至少两个连续非工作日的候选窗口，默认提前 10 天生成一轮提案。用户日历占用、明确工作安排优先于公共假日。
- 普通周末探索默认关闭，用户可开启为每月一次；法定假期探索在首次托管设置中独立展示开关。
- 提案未采纳时不连续追问；首次生成距假期不足 10 天时允许补生成一次，按窗口去重。
- 公共假日来源缺失或过期时，只按用户确认的空闲窗口提供建议，不猜测调休日期。

### FR-08 检索与现实可行性

- 本地活动上线依赖可用的外部检索工具；开放时间、价格、预约状态和交通信息注明来源，优先主办方或官方渠道。未核实值明确标注，不伪装实时可用。
- 外部检索不可用时降级为不依赖实时信息的体验方向，不生成具体活动事实。
- 初次建议核实一次；采纳时重新核实；已采纳活动出发前 24 小时内检查可能影响成行的开放状态和天气（有数据时）。发生实质变化才通知。
- 户外活动提供天气不适宜时的室内或延期选项；超出天气预报范围时标注待临近确认。
- 同一窗口最多三项提案；近 90 天已拒绝的同一活动不重复推荐，除非用户重新请求。主题层面只做降权，不永久封禁。
- 至少保留一个可自由支配的时间块；不默认把整个假期排满。用户可以选择「这次只想休息」，关闭本窗口推荐。

## 7. 跨任务记忆与协调

### FR-09 记忆内容

| 类型 | 示例 | 使用与更新 |
|---|---|---|
| 用户明确价值与偏好 | 周末想留出家庭时间 | 用户可编辑，冲突时询问取舍 |
| 决定与理由 | 先学基础再做复杂 Agent | 保存适用事项、来源、版本和重议条件 |
| 未来意图 | 等资料到齐再开始比较 | 条件出现时唤醒，完成或取消后关闭 |
| 协作经验 | 午休短练习试行后有两次进展 | 标明观察窗口和样本，不写成性格事实 |

活跃承诺、等待条件和实验状态属于结构化业务数据，不仅存进向量记忆。检索用于补充背景，不能成为判断是否完成或是否允许执行的唯一依据。

记忆必须可查看、修正、删除。删除推断记忆后记录再生抑制，不从相同旧证据立即重建；用户主动提供的新证据可以形成新的待确认判断。

### FR-10 跨事项分配

- 以明确的截止、用户优先级、可用时间、用户保护的安排为依据，不由模型自行给人生价值排序。
- 默认建议同时重点推进不超过三个成长事项，其他保留为待展开；用户可覆盖该建议。
- 时间不足时给出「保留什么、缩小什么、延后什么」的整体方案，说明影响。
- 工作紧急不自动覆盖家庭安排；跨域冲突必须进入可确认方案。
- 学习停滞不自动用一次旅游抵消；不同关切的进展分别表达，不形成统一人生积分。

## 8. 界面与文案

### 8.1 今天页

沿用现有工作区与任务结构，增加「值得留意」区域：默认只展开一条最有价值的事项，其余折叠，最多三条。排序为可行动的工作风险、已接受计划的变化、长期投入调整、探索机会。

卡片固定结构：事实 → 为什么现在值得关注 → 一个主要行动。至多三个直接操作，其他放入次级菜单。依据可展开；无候选时区域消失，不用空洞鼓励文案填充。

### 8.2 线程详情

在现有线程详情增加托管摘要：为什么重要、当前约定、最近真实进展、下一步、Vital 正在准备什么、下次检查条件。默认展示行动与当前判断，历史折叠。

用户可直接暂停、修改约定、补记进展、查看和纠正记忆。聊天从这里开启时自动携带事项上下文，方案与页面共享状态。

### 8.3 探索体验

探索作为今天页的季节性提案和独立详情，不增加无限下拉信息流。详情展示推荐原因、行程成本、现实约束与来源；选择后才进入计划。

### 8.4 视觉与语言原则

- 遵循 Mineral Garden 以及 rail / library / canvas，使用留白、排版与已有背景层级。
- 不使用红色累计欠账、连续打卡断裂、健康分、关系分、自动人格标签。
- 正向反馈指向具体事实，如「这周两次练习都解释了思路」，不空泛夸奖。
- 允许明确反馈：「这份计划连续两个周期都没有启动，值得换一种安排。」语气温和不意味着回避事实。
- 移动端主要操作无需悬停；支持键盘操作、屏幕阅读器与长文本换行。加载、失败、离线和数据不足都有独立状态。

## 9. 用户故事与验收

以下按可独立验证的功能切分；实现阶段可进一步拆成工程任务。所有 UI 故事需通过浏览器技能（本仓库采用 csi）验证桌面与移动视口，相关类型检查和 lint 通过。

### US-01 开启事项托管

作为用户，我希望一句话让 Vital 持续跟进算法学习，以便不用反复交代。

- [ ] 可从聊天或现有线程生成可编辑约定草案，包含阶段成果、节奏、下一步和权限。
- [ ] 接受后创建唯一有效约定，重试不重复创建任务；原有线程默认未托管。
- [ ] 在没有足够基础信息时只追问一个关键事实，并允许先保存草案。

### US-02 记录与补充进展

作为用户，我希望快速记录线下学习或锻炼，避免被误认为没有行动。

- [ ] 支持关联任务、手动一句话记录及补记发生时间；自报不强制上传证明。
- [ ] 修改任务标题不算进展；补记完成会撤回已不适用的候选。
- [ ] 同一进展的任务完成事件和同步重试不会重复累计。

### US-03 识别连续停滞

作为用户，我希望在连续未推进时得到有依据的反馈。

- [ ] 定时约定与周次数约定按 FR-01 分别计算，有暂停与时区边界用例。
- [ ] 无数据使用「没有记录」，不声称用户刷视频或没有运动。
- [ ] 无明确节奏的愿望不被自动判为失败。

### US-04 获得一个可开始的行动

作为用户，我希望停滞时直接得到一个小行动，降低重新开始的成本。

- [ ] 展示一个主要建议，包含耗时、入口和完成标准；不是再生成整套课程。
- [ ] 提供补记、调整、暂停入口；采纳前不更改正式安排。
- [ ] 材料缺失或生成失败时保留重试与手动选择，不显示虚假的就绪状态。

### US-05 运行并回顾纠偏实验

作为用户，我希望 Vital 记住上次调整，判断是否值得继续。

- [ ] 同一事项只有一个活跃实验；保存假设、版本和观察窗口。
- [ ] 周期结束展示实际进展与是否达约，数据不足时明确无法判断。
- [ ] 无效果时提供减量、换时段或重议目标，不原样重复旧建议。

### US-06 控制跟进负担

作为用户，我希望随时暂停与减少打扰。

- [ ] 暂停立即阻止新的候选和待执行效果；恢复不追补暂停期间机会。
- [ ] 两次未响应触发仅站内期；每日、每周预算和单事项冷却均可验证。
- [ ] 用户修改偏好后，排队中的通知在发送前应用最新设置。

### US-07 提前发现工作风险

作为用户，我希望在仍能改变结果时看到工作风险和下一步。

- [ ] 有估时与占用时可计算最晚启动窗口；数据不足时不输出确定延期结论。
- [ ] 风险包含事实、受影响承诺和具体建议。
- [ ] 风险解决、依赖完成、日期修改后旧提醒失效；同风险版本不重复推送。

### US-08 协调工作与长期投入

作为用户，我希望计划冲突时能看到整体取舍。

- [ ] 方案显示所有被调整事项及前后差异，不自动覆盖受保护安排。
- [ ] 应用前检查版本；冲突项遵循现有方案语义跳过并明确汇报，不静默覆盖。
- [ ] 应用与撤回沿用可审计的任务变更链路。

### US-09 获得假期探索建议

作为用户，我希望假期前收到少量现实可行、不同于平时的体验提案。

- [ ] 尊重调休、个人日历、所在地与可用时间，缺失数据不猜测。
- [ ] 一个窗口最多三项，具有明确推荐原因与体验差异，不输出三个同质地点。
- [ ] 「这次只想休息」关闭该窗口后续推荐，不影响其他事项跟进。

### US-10 将探索变成可执行安排

作为用户，我希望选中的体验能直接进入计划。

- [ ] 采纳时核实易变信息并注明来源；检索失败明确待核实。
- [ ] 确认后才生成任务或时间安排，重试不会重复创建。
- [ ] 临近出发发生实质变化时给出替代或延期建议，不自动预订。

### US-11 查看与修正 agent 的理解

作为用户，我希望知道判断来自哪里，并纠正错误。

- [ ] 当前判断可展开来源；自述、观察和推测有区分。
- [ ] 用户修正优先于旧推断，删除后不会由同一证据立即再生。
- [ ] 健康、家庭不出现系统评分或心理诊断。

### US-12 持续工作且可停止

作为用户，我希望离开页面后准备工作仍能继续，取消后可靠停止。

- [ ] 准备任务持久化，超时重试与 worker 重启不重复产生业务效果。
- [ ] 取消托管或删除事项后，运行中的任务在落地前校验并放弃过时结果。
- [ ] 失败、成本熔断、外部数据不可用均有明确状态；不宣称已完成。

## 10. 与现有系统的关系及工程约束

本节是对当前代码与文档的静态核对，不代表所有能力已通过线上验收。

| 已有基础 | 本轮用途 | 新增部分 |
|---|---|---|
| outcomes 与线程页面 | 承载托管事项 | 约定、跟进状态、来源和下一次检查 |
| tasks / habits / energy_logs | 行动与用户自述信号 | 进展关联、节奏机会与豁免计算 |
| agent_memory、history、distill | 检索长期背景与反馈 | 决定理由、实验经验与再生抑制核对 |
| agent_jobs、scheduler、budget | 持久调度、重试、成本控制 | 事项变化驱动判断与授权版本检查 |
| notify.scan、weekly-observe、outbox | 候选出口与通知渠道 | 有状态的介入、统一去重预算、发送前复核 |
| plan preview / apply / undo | 内部变更方案 | 纠偏与跨事项方案入口 |
| holiday_calendar | 公共假日与调休事实 | 可用窗口、探索提案与外部事实核实 |

### 10.1 数据职责建议

逻辑实体包括托管约定、进展证据、介入候选、纠偏实验、等待条件、探索提案与来源。物理表名和迁移编号留给技术设计；需要支持用户归属、版本、时间戳、软删/硬删策略和查询索引。

事件流：业务变更 → 收集受影响事项 → 规则产生候选 → 按需检索记忆/模型生成建议 → 保存候选 → 投递前复核 → 用户行动或授权执行 → 记录结果与重新判断。

事件驱动为主，每日补扫兜底。普通事项每日最多一次自动模型评估，显式用户请求不受此频率限制但仍受总预算；无新增事实复用结果。模型不负责决定权限、事务、日期边界或去重。

### 10.2 一致性与降级

- 遵守无外键约束；所有引用校验存在性与 user_id。跨表写入在一个 getDb().transaction 中完成。
- 删除父事项时同步取消待办候选和调度，并删除或去标识关联记录；不得留下可继续执行的孤立任务。软删保留恢复所需证据。
- 新表纳入 resetDb 与 eval 按用户清理；schema 变更后重启 worker。
- 幂等至少按用户、事项、约定版本、机会/风险窗口区分；重放和并发不得重复执行。
- 本地日期、周界与节假日按用户时区计算，存储事件时保留绝对时间；时区变化重新计算未来窗口，不改写历史事实。
- 规则计算可独立运行；模型不可用时仅展示有依据的事实与通用操作，不臆造个性化建议。
- 每次模型调用进入现有 capability 成本观测；新增准备工作遵守现有用户预算与熔断，不引入无限后台推理。
- 非紧急通知预算须与已有晨报、晚报、周报及提醒聚合核对，避免多能力为同一问题分别推送。
- 外部内容作为资料，不作为授权指令；用户私人记忆不得不必要地发送到外部搜索请求。

### 10.3 对旧 PRD 的修订关系

旧 PRD 的晨晚报、周报、记忆、委派、排程基础继续复用。本 PRD 对新托管体验的介入规则优先，替代固定的重复催促逻辑。

旧文案示例中「深夜建任务是不是焦虑性记录」不进入本产品；精力与完成率关联只能表述相关观察，不能称为因果。现有实现是否含此类文案需在落地时检查，不能假定已经修复。

## 11. 分期与交付门槛

### P1 长期投入闭环（首个完整可用版本）

范围：US-01 至 US-06、US-11、US-12；算法/Agent 学习和锻炼模板、进展记录、停滞判定、最小行动、一次纠偏实验、暂停和预算。只用内部资料也可完成闭环。

门槛：可在模拟时间中跑完「接受约定 → 两次未记录 → 调整 → 有进展 → 撤回旧提醒 → 回顾实验」，并以用户实际使用验证。只上线提醒、不支持调整后回顾，不算交付。

### P2 工作跟进与跨事项协调

范围：US-07、US-08；明确依赖、最晚启动风险、内部事件唤醒、保护安排与整体取舍。邮件、GitHub 等外部连接器按独立后续项目接入，不阻塞内部闭环。

门槛：风险产生与撤回、依赖解除、跨事项冲突、版本变更和撤回均通过回放。

### P3 节假日探索

范围：US-09、US-10；假期窗口、有限探索提案、采纳、临近核实和轻反馈。外部检索是具体本地活动推荐的发布前置条件；不可用时只发布通用体验方向。

门槛：覆盖调休、已有安排、未知城市、信息过期、恶劣天气、选择休息和重复生成。

三期均属于本 PRD 的目标范围；P1 是首发切片，不代表工作跟进与假期探索被取消。

## 12. 成功指标与验证

### 12.1 产品指标

首轮试用观察四周，不为了完成指标增加提醒。单用户样本只用于前后观察，不做统计显著性或因果宣称。

| 指标 | 定义 | 首轮判断方式 |
|---|---|---|
| 停滞后恢复率 | 收到纠偏后一个约定周期内出现用户进展的事件数 / 已完整观察该周期的纠偏事件数 | 与试用初期基线比较，展示分子分母 |
| 恢复耗时 | 首次满足停滞条件至下一次用户进展的时间 | 排除暂停区间，未恢复标为未结束观察 |
| 建议有效性 | 完成回顾的实验中，用户认可更容易开始或约定达成改善的实验数 | 自报与行为分别报告，不混为因果 |
| 无效打扰 | 被标为已解决、事实不对或不适合的推送数 / 已投递推送数 | 逐条检查，未响应另列 |
| 工作风险价值 | 用户确认有帮助且发生在行动窗口前的风险提示数 | 不以提醒总量为成功 |
| 探索价值 | 被采纳并由用户确认发生或有价值的体验数 | 未反馈保持未知，不算失败 |

首轮产品假设：至少观察到三次停滞后恢复、一次用户认可的工作风险提示、一个合适假期窗口中的有效探索提案。若观察期无相应场景，延长该项验证，不为凑数制造场景。以上是验证样本目标，不是效果保证。

### 12.2 发布必须满足的可靠性门槛

- 固定回放集中：暂停后投递、已解决旧提醒、跨用户引用、重复执行、预算越界均为零。
- 所有具体活动事实带来源或明确待核实；无来源的确定性事实为零。
- 所有 agent 变更可追溯；未经约定的正式写入为零。
- 日期、周期、时区、补记、撤销、worker 重启和并发重复事件有自动化覆盖。
- UI 覆盖首次使用、正常跟进、停滞、调整、暂停、离线、失败及没有候选状态。

### 12.3 必测回放清单

1. 周二、周四学习均无记录，周五补记周四学习：计数重算，旧候选失效。
2. 每周一次学习：周中未学不触发停滞；周期结束按规则检查。
3. 连续休假两周：不积累欠账，恢复后从新机会计算。
4. 修改计划后旧 job 返回：结果不写入新版本，不产生旧提醒。
5. 同时出现工作风险、学习调整和探索候选：按预算排序、聚合，不各发一次。
6. 用户没有运动记录但说明线下完成：接受自报，不要求设备证明。
7. 用户说刷视频，但未授权设备数据：只使用该次自述，不声称监测到使用时长。
8. 生成学习资料成功：只标准备完成，不标用户已经学会。
9. 假期日历显示休假，但用户有工作安排：避免安排冲突，不强行建议出行。
10. 活动取消或天气变化：撤回旧计划建议并提供替代，不继续推荐已失效活动。
11. 删除事项时准备任务正在运行：无孤立通知、无越权结果落地。
12. 模型熔断：基础状态与暂停仍可用，规则反馈可理解，不伪造智能分析。

## 13. 待验证事项与研究依据

目前没有阻塞 PRD 的用户故事问题。后续实际使用时才需要收集学习基础、具体工作承诺、所在城市、个人假期与预算等情境事实，不要求用户现在一次性补全。

上线前工程核对项：现有通知派发是否支持候选级撤回与统一预算；记忆删除抑制能力是否满足本规则；节假日数据更新来源和覆盖范围；外部检索能力、成本及失败行为。未核对的能力不得标为已交付。

产品假设需验证：两次机会/一周周期是否介入过早；每日一次每周三次是否过多；最小行动是否改善恢复；假期前十天是否有足够安排空间。通过实际反馈调整，不将默认值包装成心理学定律。
