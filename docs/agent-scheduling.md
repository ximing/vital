# Agent 调度与重启恢复

所有任务、反馈、记忆和执行记录按用户隔离。模型读取只包含当前用户的数据；业务事务按用户串行提交，同一用户的同类后台任务不会并行执行。不同用户共享可配置的全局并发上限。

## 调度

| 能力 | 默认触发策略 |
| --- | --- |
| 线程整理 | 任务变化后防抖 2 分钟；至少 4 项未完成、未归属线程且不属于习惯的任务；完成后冷却 30 分钟 |
| 线程状态 | 线程内任务变化后防抖 30 秒；每日巡检补充陈旧线程 |
| 记忆提炼 | 3 条新反馈，或 1 条修改/拒绝反馈，防抖 5 分钟；不足数量的反馈等待 24 小时；完成后冷却 30 分钟 |
| 记忆维护 | 有记忆变化时每日整理一次；内容指纹相同则不调用模型 |
| 手动操作 | 设置中的“整理线程”“更新记忆”立即入队，绕过普通冷却；同样遵守用户隔离和执行互斥 |

调度器默认每 30 秒检查一次，实际开始时间还受队列容量和模型响应影响。事件和截止时间在业务事务中写入 `agent_scheduling`，不依赖进程内定时器保存状态。扫描使用用户 ID 分页，也会覆盖没有近期任务活动但仍有待处理反馈的用户。

## 重启保证

- 等待防抖、冷却、预算或重试的工作均持久化在 PostgreSQL。
- 正常停机停止领取任务并等待在途工作结束；生产 Compose 为 worker 设置 5 分钟停止宽限期。
- 强制终止时，运行任务不会被删除。租约到期后由恢复器重新排队；默认租约 5 分钟，恢复检查沿用 `WORKER_HEAL_INTERVAL_MS`，因此不是立即接管。
- 每次领取有独立租约标识。旧执行不能提交业务结果或覆盖新执行的状态。
- 业务结果与已处理代次在同一事务提交。若业务已经提交但进程来不及标记任务完成，新执行只确认完成，不再次调用模型或写入业务结果。
- 执行期间出现的新事件使用下一代次保存，不会被当前执行的完成状态清掉。

这是持久化的至少一次执行。若进程在模型请求发出后、业务提交前被强制终止，恢复可能重新调用模型；外部模型调用不能保证只计费一次。无法确认的用量保留为未知，不按零计算。保证依赖 PostgreSQL 数据持久化，不涵盖数据库被清空或存储损坏。

## 成本与记录

每用户每日默认允许 100 次后台模型请求，按用户时区计日。请求记账与预算预占原子提交；超额任务推迟到次日且不消耗失败重试次数。手动操作不占后台预算，使用接口请求频率限制。通知先预占唯一通知记录，再改写文本；重复扫描不会重复改写，准备过程中重启可恢复持久化的规则文案。

模型超时、临时不可用、限流及已知数据库瞬时错误可重试。无效模型认证/配置及程序错误不盲目重试。后台默认最多尝试 8 次，并限制失败重试总时间为 48 小时；自然语言创建任务仍保留最多 3 次重试的独立交互策略。

系统行为展示触发原因、当前用户的数据范围、跳过原因和实际变更数量。记忆记录来源反馈的版本和时间，变更保留历史；用户手写或编辑过的记忆不会被模型覆盖。

## 配置与发布

配置示例见根目录 `.env.production.example` 与 `apps/server/.env.example`。主要配置为 `AGENT_SCHEDULER_INTERVAL_MS`、`AGENT_CONCURRENCY`、`AGENT_LEASE_MS`、`AGENT_HEARTBEAT_MS`、`AGENT_MAX_ATTEMPTS`、`AGENT_RETRY_MAX_AGE_MS`、`AGENT_DAILY_MODEL_CALL_LIMIT`。

发布前必须执行 `0026_chilly_korg.sql` 迁移。现有 Compose 的 server/worker 依赖迁移任务成功后启动；不要先启动新代码再迁移。该迁移新增状态和历史字段，不删除排队任务。

## 验证

`apps/server/__tests__/agent/restart.test.ts` 启动独立子进程，在业务提交后用 SIGKILL 终止，再由父进程恢复并确认不会重复落库。队列测试还覆盖租约心跳、旧执行失效、新事件跨重启保留和跨用户隔离。预算、反馈增量、通知预占及调度策略分别有集成测试。
